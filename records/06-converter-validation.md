## 三、編譯與測試結果

### 3.1 TypeScript 編譯檢查

執行 `npx tsc --noEmit`，沒有輸出診斷錯誤。

**結果：本次檢查未回報錯誤。**

### 3.2 自動化測試

執行 `node --test`，第一次執行結果如下：

- 測試總數：16
- 通過：15
- 失敗：1

唯一失敗發生於快照測試啟動轉換器時，Windows 回報無法刪除既有輸出檔案，錯誤為 `EPERM`。

檢查結果顯示，目標檔案不是唯讀檔案。當時發現一個 Node.js 程序，其命令列指向 SonarLint 的 ESLint Bridge，但沒有證據證明該程序造成檔案刪除失敗。

之後手動刪除該輸出檔案成功，再次執行 `node --test`，結果如下：

| 項目   | 結果 |
| ---- | -- |
| 測試總數 | 19 |
| 通過   | 19 |
| 失敗   | 0  |
| 略過   | 0  |

**結果：本次完整測試執行全部通過。**

`EPERM` 的根本原因尚未確認，不應將這次成功解讀為已找到根因或完成永久修復。

## 四、快照測試確認

以下三個輸出檔均通過與基準檔的比對：

- `build-mh/dao/Provider.js`
- `build-mh/dao/ProviderConsumer.js`

這表示在本次測試環境及輸入條件下，轉換器產生的上述輸出與既有基準一致。

## 五、特定轉換行為確認

檢查檔案：`build-mh/dao/ProviderConsumer.js`

檢查方法：使用 PowerShell 搜尋 `testObjectProperty()`，並查看其後續輸出。

實際輸出確認以下行為：

1. Shorthand property 會保留原始 property key，並將 value 轉換為對應的 `mh` 命名空間引用。
2. 一般 object property 會保留 property key，並正確轉換其 value。
3. 字串中的類別名稱不會被誤改寫。

**結果：本次實際輸出符合預期，並與已通過的快照測試一致。**

## 六、仍待確認的事項

目前已知手動刪除目標檔案成功，之後完整測試也通過，但尚未確認第一次刪除失敗的原因。

此問題暫列為未解釋、且本次未重現的異常。

這些訊息沒有導致本次測試失敗，但其來源與影響尚未確認。

目前不將它們視為已修復，也不將它們視為已證實無害。
