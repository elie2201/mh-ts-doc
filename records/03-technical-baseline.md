## 二、目前專案環境

### 2.1 專案位置與既有產物

- 專案根目錄：`Z:\share`
- 既有發布腳本：`my-mh-aid.js`
- TypeScript 原始碼目錄：`ts-src`
- TypeScript 專案設定：根目錄的 `tsconfig.json`
- TypeScript 套件版本：`^7.0.2`（以目前已知設定為準）

既有 `my-mh-aid.js` 是大型單檔使用者腳本。TypeScript 移轉不得以改變最終發布形式為前提。

### 2.2 目前 `tsconfig.json`

目前已知設定如下：
```
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": ["ts-src/**/*.ts", "ts-src/**/*.d.ts"],
  "exclude": ["node_modules", "build"]
}
```

目前專案型別檢查命令：
```
npx tsc -p .\tsconfig.json
```

此設定的用途是檢查 TypeScript 原始碼，不直接輸出 JavaScript。

`strict: true` 是重要的品質要求，不應為了消除個別錯誤而任意降低整體型別檢查標準。

## 三、已確立的技術方向

### 3.1 使用 `import`／`export` 模組化開發

已決定維持 TypeScript 原生的 `import`／`export` 寫法，不改採以 `declare namespace` 作為主要原始碼組織方式。

理由：

- 原始碼可以按類別及責任分檔。
- 可以依功能及架構分目錄。
- 模組依賴關係能直接表達在程式碼中。
- 能利用 TypeScript 的型別檢查及編譯工具鏈。
- 不必為了維持全域命名空間而犧牲原始碼的模組化。

### 3.2 原始碼分層與目錄組織

設計方向是維持多檔案、多目錄的組織方式，避免將所有 TypeScript 程式碼集中到單一大型檔案。

目前規劃的架構目錄包括：

- `data`
- `dao`
- `cmd`
- `core`
- `utils`
- `chk`
- `addon`

預期可依目錄及責任區分同名類別，例如：

- `mh.data.ProloguePond`
- `mh.dao.ProloguePond`
- `mh.cmd.ProloguePondFactory`
- `mh.core.ProloguePond`

以上是預定的命名及架構方向，不代表所有類別都已完成移轉或驗證。

### 3.3 保留既有 `mh` 全域物件

既有 JavaScript 系統已建立 `mh` 全域物件，TypeScript 移轉必須與其相容。

既有程式碼的基本形式為：
```
const mh = {};
unsafeWindow.mh = mh;
```

後續還有既有的 `mh` 成員及子命名空間。

因此，移轉時必須避免：

- 意外重新建立或取代既有的 `mh` 物件。
- 因模組初始化方式而破壞既有成員。
- 讓同名類別在不同子命名空間中互相覆蓋。
- 只因 TypeScript 編譯成功，就推定最終整合結果正確。

### 3.4 最終發布仍為單一 JavaScript 檔案

目前採取的方向是：

1. 以 TypeScript 多檔案開發。
2. 透過編譯及必要的轉換處理，產生符合既有 `mh` 全域架構的 JavaScript。
3. 將產出整合進既有的 `my-mh-aid.js`。
4. 逐步測試整合後的功能。

已安裝 `esbuild` 作為開發依賴，但實際採用的完整輸出轉換流程及所有輸出情境，仍須以實際測試確認。

## 四、型別設計原則

### 4.1 重視可由編譯器驗證的契約

本專案使用 TypeScript 的核心價值，不只是語法提示，而是希望在開發階段驗證類別之間的契約。

設計時應優先考慮：

- `interface`：定義資料及依賴契約。
- `abstract class`：建立共同行為及必要的擴充規則。
- 明確的參數及回傳型別。
- 可檢查的依賴關係。
- 適當的型別限制，避免錯誤一路傳遞到執行階段。

### 4.2 避免以放寬型別掩蓋問題

不得僅為了讓編譯通過，就任意使用 `any`、過度寬泛的型別或不必要的型別斷言。

若遇到無法正確表達的型別，應先釐清問題來源，再決定如何修正契約或補充型別宣告。

### 4.3 依賴注入與介面設計

介面是本專案表達依賴契約的重要工具。

設計時應避免因依賴項目持續增加而形成難以維護的參數列表，也應避免依賴關係只在執行到特定程式碼時才暴露錯誤。

實際採用何種注入方式，仍須依具體類別及使用情境決定，不應將單一模式強制套用到所有程式碼。

## 五、舊宣告檔產生流程的處理方向

過去曾使用 `scripts/generate-mh-dts.js` 等流程產生 `mh.d.ts`，並搭配監看程式處理檔案變更。

已知問題是監看程序在沒有實際編輯時仍持續消耗 CPU，造成不必要的背景負擔。

因此，已確立的方向是以 TypeScript 原生型別檢查為主要開發期保障，降低對常駐宣告檔產生程序的依賴。

但應區分以下兩件事：

- **已確立的目標**：不再依賴不必要的常駐宣告檔產生流程。
- **尚待逐步確認的工作**：既有 JavaScript、遊戲全域變數及舊類別如何完整接入新的型別系統。

不能因為新 TypeScript 專案能通過檢查，就推定所有舊 JavaScript 都已獲得完整型別保障。

## 六、已知的驗證邊界

目前不能直接推定下列事項已全部完成：

1. 所有 TypeScript 類別均已完成移轉。
2. 所有既有 JavaScript 及遊戲全域物件均已有完整型別宣告。
3. 所有 `export` 成員都能正確轉換成預期的 `mh` 命名空間成員。
4. 類別與常數均能透過同一套轉換規則正確輸出。
5. 不同子命名空間中的同名類別及常數不會發生衝突。
6. 產生的 JavaScript 已在實際 mh 環境中完成完整測試。
7. 整份 `my-mh-aid.js` 已完成 TypeScript 移轉。

後續工作應以實際測試結果逐項更新狀態，不應一次將上述事項全部標記為完成。
