# mh TypeScript 移轉｜專案基準與已定案決策

## 一、紀錄目的

本紀錄保存 TypeScript 移轉專案目前已確認的技術路線、架構決策、開發環境資訊及工作基準，供後續工作查閱與接續。

本紀錄中的決策，除非後續工作經過明確討論並正式修訂，否則應視為後續實作的共同基準。

必須區分以下狀態：

- **已定案**：已確認採用的設計或技術路線。
- **已驗證**：已實際執行測試或檢查，並取得相應結果。
- **待驗證**：已有設計方向，但尚未取得足以確認結果的證據。
- **待辦**：尚未完成的工作。

不得將設計提案、預期行為或編譯成功，直接視為整合及執行驗證已完成。

## 二、已定案的技術路線

### 2.1 開發語言與模組系統

- 新功能及逐步移轉的既有功能採用 TypeScript。
- 原始碼維持 `import`／`export` 模組化開發方式。
- 原始碼可以分成多個檔案及目錄，不為了方便編譯而集中在單一大型檔案。
- 不因最終發布為單一 JavaScript 檔案，就犧牲開發階段的模組化、型別檢查及架構清晰度。
- 最終發布的 `my-mh-aid.js` 仍維持單一 JavaScript 使用者腳本，不要求使用者端額外載入多個模組。

### 2.2 編譯與整合方向

- 使用 TypeScript 原生編譯器進行型別檢查及必要的 JavaScript 輸出。
- 已安裝 `esbuild` 開發依賴，作為後續模組整合與單檔輸出的工具選項。
- 初期採漸進式移轉：新 TypeScript 功能經過編譯後，再整合至既有 `my-mh-aid.js`。
- 不以一次重寫整份既有腳本為前提。
- 是否擴大至整份主程式的 TypeScript 移轉，依實際成果再評估。

**尚待驗證：** `esbuild` 的實際輸出方式、與既有 `mh` 全域命名空間的整合，以及最終單檔輸出是否符合所有既有執行需求。

### 2.3 型別檢查與宣告檔

- 專案的主要目的，是利用 TypeScript 的靜態型別檢查、介面契約及編譯期錯誤偵測。
- 不再以持續執行的自製宣告檔產生器作為主要開發流程。
- 不以「能產生 JavaScript」或「編譯成功」單獨作為移轉成功的判準。
- 優先保留明確型別及契約，不為了消除編譯錯誤而任意放寬型別。
- 開發工具應避免不必要的常駐背景工作，降低持續 CPU 使用率及其他資源負擔。

## 三、既有系統整合原則

### 3.1 `mh` 全域命名空間

既有腳本以 `mh` 作為全域命名空間。新程式必須能與此架構整合，不得因編譯輸出而意外覆蓋或破壞既有的 `mh` 物件及其成員。

開發階段可以使用模組化的 TypeScript 原始碼；最終輸出則必須符合既有使用者腳本的執行環境要求。

### 3.2 舊執行環境的全域依賴

抽象類別應盡可能在 `mh` 架構內自給自足，不直接依賴舊腳本的全域物件。

例如 `$`、`user`、`eventRegistry`、`jsDialog` 等既有環境依賴，應由實際需要它們的實作層處理。

對已確認存在的全域依賴，可透過適當的 `/* global ... */` 宣告處理 ESLint 警告；不應因此將這些依賴任意引入所有抽象類別。

### 3.3 漸進式相容

- 新程式必須能與既有 JavaScript 類別及全域物件共存。
- 逐步將既有類別轉為 TypeScript，不要求一次改變所有呼叫端。
- 每個整合階段都應區分型別檢查、編譯輸出、整合驗證及實際執行驗證。
- 若新舊程式之間存在型別資訊不足的邊界，應明確界定並逐步改善，不應假設既有 JavaScript 程式已自動受到完整的 TypeScript 型別保障。

## 四、架構分層與依賴方向

主要分層及依賴方向已定案如下：

`mh.data → mh.dao → mh.cmd → mh.core`

各層的預定責任：

| 層級         | 命名空間      | 主要責任         |
| ---------- | --------- | ------------ |
| Data Model | `mh.data` | 資料結構及領域資料    |
| Repository | `mh.dao`  | 資料存取及資料來源抽象  |
| Service    | `mh.cmd`  | 功能組合、服務流程及工廠 |
| Controller | `mh.core` | 控制流程及功能協調    |

上述箭頭表示上層可依賴下層，不應反向形成不必要的循環依賴。

類別可依架構層級使用相同的主體名稱，例如：

- `mh.data.ProloguePond`
- `mh.dao.ProloguePond`
- `mh.core.ProloguePond`

這種命名方式有助於表達同一領域概念在不同層級的責任差異；實際類別名稱仍須依其責任及既有設計確認。

既有 `TravelPlan` 的設計屬於待後續處理的例外，暫不納入本階段重構；之後預計改寫為 `extends mh.data.Config`。

## 五、正式移轉的優先順序

### 5.1 第一批參照類別

以 `mh.data.ForewordFarm` 相關類別作為正式移轉的第一批。

`mh.data.ProloguePond` 作為第二參照，用於比較及驗證不同類別的移轉方式。

兩者的 Data Model 已完成。這代表資料模型已有既定基礎，但不代表相關 DAO、Service、Controller 或最終整合工作均已完成。

### 5.2 先處理抽象類別

移轉順序已定案：

1. 抽象 Provider。
2. 抽象 Repository。
3. `AjaxProvider`。
4. 具體子類別。
5. 依賴上述類別的 Service、Controller 及其他必要整合。

先建立抽象層的型別與契約，再移轉具體實作，避免不同實作各自形成不一致的介面。

實際類別清單及每個類別的完成狀態，應以後續工作紀錄為準，不應僅憑預定順序推定已完成。

## 六、開發與驗證原則

### 6.1 型別契約優先

- 適當使用 `interface`、`abstract class` 及明確型別。
- 讓依賴關係與呼叫契約能由編譯器檢查。
- 避免僅能在執行時期才能發現的錯誤。
- 不為了快速通過編譯而任意放寬型別。
- 當型別系統無法表達某項設計限制時，應明確指出限制，而非假設編譯成功即代表限制已受到保障。

### 6.2 保留既有架構意圖

實作時不應只追求輸出結果可執行，也要保留既有設計的語意。

例如，若抽象方法刻意宣告為 `async`，是為了要求子類別遵循非同步介面契約，就不應僅為消除靜態分析警告而任意移除 `async`。

### 6.3 區分驗證層級

後續紀錄應清楚區分：

1. **型別驗證**：TypeScript 能否檢查預期的型別及契約。
2. **編譯驗證**：原始碼能否成功編譯及輸出。
3. **整合驗證**：產生的程式能否正確整合至既有主程式，且不破壞既有結構。
4. **執行驗證**：整合後的實際行為是否符合預期。

未完成的驗證不得以其他層級的成功取代。

以下是目前已知的環境資訊，供排查工具及編譯問題時參考：

- Node.js：`v22.18.0`
- npm：`10.9.3`
- 專案本機 TypeScript：`5.4.5`
- VS Code 內建 TypeScript：`6.0.4`
- 已安裝 `esbuild` 開發依賴。
- 專案使用 ES Module 套件設定（`"type": "module"`）。
- 過去曾使用自製宣告檔產生器及檔案監看程序；新流程的目標是避免不必要的常駐背景工作。

以上版本是已知紀錄，不代表目前已更新至最新版本。實際編譯與診斷應以當下使用的工具版本及設定為準。

## 八、待後續工作確認的事項

以下事項不因本紀錄建立而視為已完成：

- 確認 TypeScript 專案設定及實際編譯流程符合漸進式移轉需求。
- 驗證 `import`／`export` 原始碼如何穩定整合至既有 `mh` 全域命名空間。
- 驗證 `esbuild` 輸出是否符合單一使用者腳本的整合要求。
- 完成抽象 Provider、Repository 及具體實作的移轉與測試。
- 驗證編譯輸出不會覆蓋、重複建立或破壞既有全域物件。
- 確認開發期型別提示、編譯期檢查及實際執行結果均符合專案目標。

- **工作項目**：本次處理的問題或類別。
