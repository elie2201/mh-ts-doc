# MouseHunt TypeScript 移轉｜專案目標

## 一、專案目的

將現有的 MouseHunt Tampermonkey 使用者腳本逐步移轉至 TypeScript 開發，以利用靜態型別檢查、介面契約及編譯期錯誤偵測，降低開發過程中的不確定性與執行期錯誤。

移轉採取漸進式策略，不以一次重寫整份腳本為前提。

## 二、核心目標

1. **導入 TypeScript 靜態型別檢查**：盡可能在編譯階段發現型別不符、介面不一致及其他可由型別系統檢查的問題，而不是等程式執行到相關路徑才發現錯誤。
2. **建立清楚的架構與契約**：透過 `interface`、`abstract class`、型別定義及明確的依賴關係，讓模組間的責任與呼叫契約容易理解、檢查及維護。
3. **維持漸進式移轉能力**：新功能及既有功能可以逐步轉為 TypeScript，不要求立即將整份大型使用者腳本全部改寫。
4. **保留現有的發布形式**：最終發布的 `my-mh-aid.js` 仍維持單一 JavaScript 使用者腳本，不要求使用者端額外載入多個模組。
5. **降低開發工具的持續負擔**：以 TypeScript 原生型別檢查取代過去造成持續 CPU 使用率的宣告檔產生流程，避免不必要的背景工作。
6. **保留既有系統的相容性**：移轉後的程式必須能與既有 MouseHunt 腳本架構、全域物件及相關執行環境整合。

## 三、架構與開發原則

- TypeScript 原始碼可以依功能及架構分層，採用多檔案、多目錄的組織方式；不為了方便編譯而將所有程式集中在單一大型原始碼檔案。
- 維持 `import`／`export` 模組化開發方式。
- 讓類別、介面及模組的責任清楚，避免因為參數或依賴關係變動而造成大量難以追蹤的修改。
- 優先使用可由編譯器驗證的契約，避免僅為通過編譯而任意放寬型別。
- 以現有 `mh` 全域命名空間及單一檔案發布需求為整合基礎，不應無意間破壞既有全域物件或功能。
- 對尚未驗證的設計、轉換方式及執行結果，必須明確標示其驗證狀態，不得將預期行為直接視為已完成。

## 四、專案成功標準

本專案不只要求 TypeScript 程式碼能通過編譯，還必須逐步確認：

1. 型別檢查能提供實際的開發期保障。
2. 模組與架構符合預定的設計原則。
3. 產生的 JavaScript 能正確整合至既有的 `my-mh-aid.js`。
4. 整合後的功能及執行行為符合預期。
5. 開發流程不再依賴不必要的常駐宣告檔產生程序。

## 五、工作流程原則

- 先釐清整體架構與目標，再處理局部實作，避免只修正眼前問題而偏離整體設計。
- 每次工作聚焦於當前問題，不重複確認已經確立的前提或決策。
- 區分已確認事實、設計提案、尚待驗證的假設及已完成的實作。
- 重要決策及里程碑應留下正式紀錄，後續工作以既有紀錄為依據；若目標或決策改變，應明確記錄變更原因與影響。
