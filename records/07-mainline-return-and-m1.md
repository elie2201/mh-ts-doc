# MouseHunt TypeScript 移轉｜主線回歸與下一階段工作基準

語法轉換器已完成一輪階段性驗證。本專案接下來回到 MouseHunt TypeScript 移轉主線，不再以完成通用語法轉換器作為前置條件。

本紀錄確立主線的工作範圍、既有架構決策、下一階段驗證順序及完成判準。

## 三、已確立的架構決策

### 3.1 保留模組化 TypeScript 開發方式

繼續採用 `import`／`export`，以獨立檔案及目錄組織程式碼，讓模組依賴能在開發階段明確表達，並利用 TypeScript 的靜態型別檢查降低執行期才發現錯誤的風險。

### 3.2 保留既有 `mh` 全域物件

轉換後的程式碼必須相容於 MouseHunt 現有的 `mh` 全域命名空間架構，不可因建置過程而取代或重新建立既有全域物件。

### 3.3 維持單一檔案發布

開發階段可以使用多個 TypeScript 模組；正式發布仍須產生單一 JavaScript 使用者腳本，並能整合至既有的 `my-mh-aid.js` 工作流程。

### 3.4 語法轉換器採漸進式擴充

原型專案 `Z:\share\ts-mh-prototype` 暫時保留為轉換器研究及測試場所。

後續只有在主線遇到實際轉換需求時，才補充對應能力及測試。待主線工作完成或有額外時間時，再評估通用化。

## 四、下一階段里程碑

### M1：確認主線現況並建立可驗證的整合基準

本里程碑的目標不是立即改寫大量程式碼，而是先確認現有成果可以如何接回正式移轉流程。

依序完成：

1. 核對 `ts-src` 的實際目錄、檔案及目前實作進度。
2. 執行主線 TypeScript 型別檢查，確認目前是否存在診斷錯誤。
3. 確認現有模組的匯入、匯出、類別引用及命名空間映射規則。
4. 確認建置流程如何將模組化 TypeScript 轉換為相容於既有 `mh` 全域物件的 JavaScript。
5. 確認建置輸出如何與 `my-mh-aid.js` 整合，並維持單一檔案發布形式。
6. 針對實際輸出執行必要測試，確認不只是編譯成功，而是輸出結構及引用關係也正確。

上述項目均為待驗證工作，不預設已經完成。

## 五、M1 的完成判準

必須以實際結果確認以下事項：

- 主線原始碼及依賴關係已清楚掌握。
- TypeScript 檢查結果已記錄。
- 模組至 `mh` 命名空間的轉換規則已明確。
- 建置結果符合單一檔案發布需求。
- 至少有可重複執行的驗證流程，能檢查輸出是否符合預期。
- 已知問題、未驗證事項及下一個實作目標均有明確紀錄。

不能只因檔案存在、程式碼已撰寫或型別檢查通過，就宣稱整合完成。

## 六、工作順序與範圍限制

目前優先順序如下：

1. 回到 MouseHunt TypeScript 主線。
2. 確認目前實際進度及整合缺口。
3. 建立可重複驗證的建置與測試流程。
4. 依主線需求逐步完成移轉。
5. 遇到新語法情境時，才擴充語法轉換器。
6. 待主線工作完成或有餘裕時，再評估轉換器通用化。

不得因追求轉換器的完整性而無限延後主線工作。
